# 前后端分离 + 权限驱动前端方案

## 一、现状分析

```
浏览器 ← Jinja2 渲染 ← FastAPI 直接返回 HTML
         ↑
   无 token、无用户概念、无权限校验
```

| 维度 | 现状 | 问题 |
|------|------|------|
| **页面渲染** | FastAPI `render_template()` 返回 HTML | 前端和后端绑死，无法独立部署 |
| **权限** | `core/security.py` 有完整的 JWT+角色系统 | **未启用**，没有任何路由加权限装饰器 |
| **前端** | 4 个 Jinja2 页面 | 所有按钮对所有用户可见，不管有没有权限 |
| **API** | `/api/*` 路由已存在 | 无认证，任意访问 |

---

## 二、目标架构

```
┌─────────────────────┐         ┌──────────────────────┐
│    前端 (浏览器)      │   HTTP   │      后端 FastAPI     │
│                     │ ◄──────► │                      │
│  Jinja2 页面(过渡)    │  JSON   │  /api/auth/*   登录   │
│  ↓                   │         │  /api/auth/me  权限   │
│  JS 根据权限显隐 UI    │         │  /api/search   检索   │
│                     │         │  /api/ask      问答   │
│  未来: 独立 SPA       │         │  ...                  │
└─────────────────────┘         └──────────────────────┘
                                         ↑
                                  security.py 正式启用
                                  JWT + 角色 + 权限装饰器
```

### 核心原则

**权限由后端定义，前端根据后端返回的权限列表动态渲染。**

```
后端定义:                                   前端表现:
admin  → 所有功能可见                      管理员看到所有
editor → 上传/编译/问答可见，管理不可见      编辑看不到「用户管理」
viewer → 仅图谱/问答可见，上传/编译不可见    浏览者看不到「上传」「编译」
api    → 仅 API 可调，页面不可见            API 用户看不到任何页面
```

不是前端 decide 显示什么，是后端告诉前端「你能看到什么」。

## 三、权限矩阵

### 3.1 角色定义（已在 security.py）

```python
ROLE_HIERARCHY = {
    "admin":  100,  # 全部权限
    "editor":  50,  # 内容操作
    "viewer":  10,  # 只读浏览
    "api":      5,  # 仅 API 访问
}
```

### 3.2 功能点与权限映射

| 功能点 | admin | editor | viewer | api |
|--------|-------|--------|--------|-----|
| 图谱浏览 | ✓ | ✓ | ✓ | × |
| 智能问答 | ✓ | ✓ | ✓ | × |
| 上传文档 | ✓ | ✓ | × | × |
| 编译运行 | ✓ | ✓ | × | × |
| 图谱管理 | ✓ | × | × | × |
| 用户管理 | ✓ | × | × | × |
| 系统配置 | ✓ | × | × | × |
| API 调用 | ✓ | ✓ | ✓ | ✓ |

### 3.3 后端返回的权限列表

```json
// GET /api/auth/me 返回
{
  "user": {
    "id": "u_001",
    "username": "admin",
    "role": "admin",
    "role_level": 100
  },
  "permissions": {
    "page:graph": true,
    "page:chat": true,
    "page:upload": true,
    "action:build": true,
    "action:admin:users": true,
    "action:admin:config": true
  }
}
```

前端根据 `permissions` 对象决定 DOM 元素的显隐，**不是在前端写死角色判断**。

## 四、分阶段实施

### Stage 1 — 后端 Auth API + 权限启用（1-2 天）

**目标**：后端认证跑通，`security.py` 正式启用

| 改动 | 说明 |
|------|------|
| `web/routes/auth_routes.py` (新增) | `POST /api/auth/login` 登录、`GET /api/auth/me` 当前用户+权限列表 |
| `core/security.py` | 补一个用户数据库（简单 JSON 文件，未来可换数据库），新增 `get_permissions(role)` 函数 |
| `web/routes/agent_routes.py` | 给每个 API 路由加 `@require_role()` 装饰器 |
| `web/app.py` | 注册 `PermissionMiddleware`，注册 `auth_routes`，`run.py` 改 JWT 密钥从配置文件读 |

**产出**：
- API 全部带上权限校验
- 前端可以在浏览器 DevTools 调 `GET /api/auth/me` 看到自己的权限
- 旧的 Jinja2 页面仍然能打开（公开路径已配置）

### Stage 2 — Jinja2 前端权限显隐（1 天）

**目标**：前端根据后端权限动态显示/隐藏元素，保留 Jinja2 模板

```javascript
// web/static/js/auth.js (新增)
// 页面加载时获取权限列表
async function initAuth() {
  const resp = await fetch('/api/auth/me', { credentials: 'include' })
  if (resp.ok) {
    const data = await resp.json()
    window.__permissions = data.permissions
    window.__user = data.user
    applyPermissions()
  } else {
    // 未登录，跳转登录页
    window.location.href = '/login'
  }
}

// 根据权限显隐元素
function applyPermissions() {
  document.querySelectorAll('[data-perm]').forEach(el => {
    const required = el.dataset.perm
    if (!window.__permissions[required]) {
      el.style.display = 'none'  // 隐藏而非 disable
    }
  })
}
```

```html
<!-- Jinja2 模板改动示例 -->
<a href="/upload" data-perm="page:upload">上传</a>
<button data-perm="action:build" onclick="startBuild()">开始编译</button>
```

| 改动 | 说明 |
|------|------|
| `web/static/js/auth.js` (新增) | 权限初始化 + `applyPermissions()` |
| `web/templates/login.html` (新增) | 登录页 |
| `web/templates/dashboard.html` | 导航栏加 `data-perm` 属性 |
| `web/templates/graph.html` | 管理按钮加 `data-perm` 属性 |
| `web/templates/chat.html` | 无改动（viewer 可见） |
| `web/templates/upload.html` | 页面整体加 `data-perm="page:upload"` |

### Stage 3 —— API 文档化 + CORS（0.5 天）

**目标**：让前端可以独立部署（跨域调用 API）

```python
# web/app.py
from fastapi.middleware.cors import CORSMiddleware
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],  # 未来 SPA 的来源
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

| 改动 | 说明 |
|------|------|
| `web/app.py` | 加 CORS middleware |
| `web/routes/agent_routes.py` | API 返回统一格式：`{"code": 0, "data": ..., "error": ""}` |

### Stage 4（可选）— 独立 SPA

当 Jinja2 页面不够用的时候，用 React/Vue 逐步替换。后端 API 不变，前端可以复用你 `ai-material-review` 项目的 React 技术栈（Vite + TypeScript + Zustand + Ant Design）。

```
novel-spa/          ← 新项目，独立目录
├── src/
│   ├── api/        ← 调后端 /api/*
│   ├── pages/      ← 图谱/问答/上传/管理
│   └── components/ ← 通用组件
├── package.json
└── vite.config.ts
```

## 五、建议不做的事

| 事项 | 原因 |
|------|------|
| **OAuth2 第三方登录** | 当前阶段不需要，增加复杂度 |
| **RBAC 动态配置界面** | 4 个角色写死就够了，未来需要再做成可配置 |
| **WebSocket 权限** | 当前 SSE 流不需要额外鉴权（复用 HTTP header） |
| **Session 管理** | 无状态 JWT 更适合前后端分离 |

---

## 六、实施顺序建议

```
Stage 1 (后端 Auth) ─── Stage 2 (前端显隐) ─── Stage 3 (CORS)
    1-2 天                   1 天                  0.5 天
```

**Stage 1** 是前提——后端认证不跑通，前端显隐没意义。
**Stage 2** 是核心——让前端真正根据权限隐藏元素。
**Stage 3** 是为未来独立 SPA 铺路。
